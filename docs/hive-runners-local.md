# Run private CI jobs on local hardware

The local controller registers one ephemeral worker for each admitted queue slot. One controller can serve multiple private GitHub repositories or GitLab projects across multiple nodes. Existing SSH, Terraform, ARC, GitLab Helm and fleet billing deployments continue to use the [fleet operator guide](hive-runners.md).

## Install, configure and start

Install Node.js 24, Docker in Linux-container mode and the Hive Runners package. Choose a Docker context connected to the intended engine. On Docker Desktop, identify the host filesystem holding its disk image in the Docker Desktop settings. On Linux Engine, use the filesystem holding the Docker data root. The controller measures the host and engine independently. If the engine runs remotely or in a VM, include a trusted probe for the host that actually backs the VM or engine data, in addition to the controller's own machine.

```sh
npm install -g @link-assistant/hive-runners
docker pull alpine@sha256:469c9ea410b9215eaee7976ba6c0639039b444be8e5d638f7abbada189971eb2
hive-runners local-probe --storage /path/on/physical/build/filesystem --json
hive-runners local-probe --docker-context default --monitor-image alpine@sha256:469c9ea410b9215eaee7976ba6c0639039b444be8e5d638f7abbada189971eb2 --json
```

Build the supplied [worker image](../examples/hive-runners/local/Dockerfile) from the repository root. Use a supported, current runner base pinned to a digest. The GitHub build expects the upstream runner under `/home/runner`. For GitLab use a GitLab Runner base with the shell executor and the tools your jobs require. The image must contain `/opt/hive-worker`, use UID/GID 1000, and declare zero Dockerfile volumes. Push the result to a registry you control, then pull its exact digest onto each selected node. For a multi-architecture repository, verify the pinned manifest resolves to the native architecture on every selected node.

```sh
docker build --build-arg RUNNER_IMAGE="$PINNED_RUNNER_BASE" \
  -t "$WORKER_IMAGE_TAG" -f examples/hive-runners/local/Dockerfile .
docker push "$WORKER_IMAGE_TAG"
docker pull "$PINNED_WORKER_IMAGE"
```

Copy the [example configuration](../examples/hive-runners/local/config.example.json) to `hive-local.json`. Set the controller storage path, runtime context, engine ID, resource identities from both probe outputs, worker image digest, and your private project. Match `amd64` to Docker's `x86_64` and `arm64` to `aarch64`. The mode in Docker Desktop must be Linux containers. The controller can run on macOS or Windows while the worker reports Linux. Set the state directory and config permissions for the local controller account. Windows paths use JSON backslash escaping and require private ACLs for the token and state directory.

Use an administrator credential in each pool's `tokenFile`. On Unix set mode 0600. For GitHub the credential needs repository Actions read access and administration permission for self-hosted runner registration and deletion. For GitLab it needs private project and job read access plus runner creation and management permission. Local workers receive a single GitHub JIT configuration or a newly minted GitLab project runner token. Each GitLab runner is locked to that private project and accepts only its dedicated tag. The controller revokes the registration after exit. Rotate the administrator credential by atomically replacing the file at the same path. The next poll reads the replacement. Keep local jobs within your trusted private project.

Queue private jobs with the pool's sole custom `runs-on` label or sole GitLab tag. Use a distinct label or tag for each target OS and architecture and for this controller's pool. The provider assigns the queued job to a matching worker. A job ID guides capacity sizing and deduplication. Provider assignment can use another compatible job from the same pool.

```sh
hive-runners local-start --config hive-local.json --state hive-local-state
hive-runners local-status --state hive-local-state --json
hive-runners local-drain --state hive-local-state
hive-runners local-resume --state hive-local-state
hive-runners local-stop --state hive-local-state
```

Start runs in the foreground. Drain pauses registrations and lets workers already admitted serve at most one job each. A job that has already started keeps its limits through completion. The controller never preempts a running job in response to resource pressure. Wait for `active: 0` before servicing a node or changing config. Stop requests drain and exits when all leases settle. On an idle GitHub JIT slot, provider matching and removal can take longer than a job; provider-side cancellation or manual deregistration requires checking that the runner is idle. GitLab's one-shot runner waits up to 60 seconds to take a job. After a crash, restart with the original config and state directory. Restart resumes the persisted desired mode and reconciles worker objects before admitting more jobs. Use one controller per physical host and runtime cluster. It holds loopback port 32764 while running. The state directory is single-writer and local to that host. Keep it through upgrades and restarts. To restart a previously stopped controller in admission mode, run `local-resume` before `local-start`.

## Host and per-node admission

The default is 49% of live available CPU, RAM and each configured filesystem. Use `{"basis":"free","percentage":50}` for half of currently free resources, or `{"basis":"total","percentage":70}` for a dedicated host. Dedicated mode accepts 50–80% and also caps the budget at currently available capacity. CPU uses millicores. RAM and storage use MiB. Set CPU, memory and storage overhead on the controller's scope. Reserve backend or hypervisor overhead through each scope's optional `overhead` map. Worker limits include the runner and nested build processes. The container memory claim adds the maximum tmpfs size to `memoryMiB`, including 16 MiB for temporary and shared-memory mounts. The storage claim includes that same workspace allowance and temporary allocation.

Each scope subtracts its controller overhead and the full claims of active and starting leases. It credits only usage that a trusted probe can attribute to an individual lease and that the same sample counted against availability. The absolute availability gate remains in force. Built-in probes make zero attribution, so an active worker already reflected in host-level usage can reduce admissions conservatively. Keep resources that draw on the same physical host in a common scope shared by its nodes. Include every backing filesystem that can fill. The controller chooses among eligible nodes using their most constrained resource. Missing, stale, out-of-range or mismatched samples prevent admission for any placement that requires them. Valid measurements let admissions resume automatically. The free reserve is measured at admission and can change when unrelated processes allocate resources. CPU and RAM ceilings and workspace limits constrain each worker; external processes, daemon metadata, fixed read-only images and the hypervisor still count toward physical resource pressure. The controller does not guarantee a continuous physical reserve against those writers.

Container workers get a read-only root filesystem, a bounded RAM-backed workspace per worker, bounded temp space, unprivileged credentials and no host mounts or daemon socket. Ordinary child processes and unprivileged build daemons inside the worker share the same limits. Privileged Docker-in-Docker, host Docker sockets, services provisioned outside the worker boundary, host workspaces and Windows containers are rejected or unavailable in these worker specs. OCI builders that need elevated mounts require a separately verified contained worker environment. Container image layers, engine and kubelet metadata, and the host or VM itself need independent monitoring. Keep images preloaded and set runtime log rotation. The Docker and Swarm specs disable the daemon log driver for these workers. The packaged entry point sends job logs through the CI provider.

## Swarm and Kubernetes nodes

For each Swarm node set `backend: "swarm"`, the Docker manager `context`, the node's pinned ID (`identity`), and exact hostname (`target`). A worker gets a one-replica, non-restarting service constrained to its node ID. Its workspace is node-local and dies with the task. Use artifacts and caches through the CI provider for durable data. Add every manager-authorized, measured node to the pool for distribution.

For Kubernetes set `backend: "kubernetes"`, a `kubectl` context, a dedicated `namespace`, exact node name (`target`) and Kubernetes node UID (`identity`). Have an administrator label the node `hive-runners.node-restriction.kubernetes.io/node-uid=<pinned UID>` and enable Kubernetes NodeRestriction so kubelets cannot assign this label. Grant the controller credentials read access to Nodes and namespace-scoped create, list and delete access to Pods and Secrets. Every worker uses node affinity and native architecture labels, a restricted pod security context, CPU and memory requests and limits, and sized memory-backed `emptyDir` volumes. Ensure the namespace allows the pod specification and resource quotas. Check that the kubelet actually applies CPU and tmpfs size limits and that the container runtime uses the filesystem your probe measures. Configure a separate scope for the physical backing resources if a Kubernetes node runs inside a Docker container or VM.

Standalone clusters, Minikube, kind, k3s and Docker Desktop Kubernetes use the same Kubernetes interface. Import the images on the exact node (for example using the distribution's image-loading feature) and verify digest visibility in the node's `status.images`. Use dedicated or trusted hosts on which the operator can collect authenticated node-local telemetry. For kind and container-driver Minikube, measure both the runtime node and the enclosing host or VM. Recording physical measurements twice as independent scopes is conservative. Multiple logical nodes sharing a machine must reference the same physical scope.

For Swarm, Kubernetes and external native adapters, each `runtimeScope` needs a `probe`. This is an argument array beginning with an absolute executable. It can be an SSH command with independently verified host keys to a node operator running the [example node probe](../examples/hive-runners/local/node-probe.mjs), or a local trusted executable. The example uses a local Docker Engine for Swarm, or a restricted kubeconfig for a Linux Kubernetes node. Its private JSON configuration contains `backend`, a map named `storage` of `fs-*` keys to local paths, an `images` array of preloaded digests, and `workspaceLimitsVerified: true` after an operator verifies the actual limits. Kubernetes also needs `context`, `node`, and `cpuLimitsVerified: true` and `memoryLimitsVerified: true` after the operator has confirmed kubelet enforcement. Confirm the runtime's root filesystem, image filesystem if separate, and every underlying host filesystem by comparing their independent resource identities. The example is for directly accessible Linux nodes and is a starting point for installations that have a separate VM, image filesystem or runtime control plane.

The probe reads `{"nonce":"…","leases":[…]}` from stdin and returns one JSON sample. Echo the nonce, report the independently checked host `identity` and remote runtime node `runtimeIdentity`, set `observedAt` to UTC epoch milliseconds, and return all `resources` with individual `identity`, `total`, `available` and, if available, a `usage` map keyed by current lease ID. With Swarm and Kubernetes the probe must also confirm `checks.cgroupV2`, `cpuLimits`, `memoryLimits`, `workspaceLimits`, `swapDisabled` and the preloaded digest in `checks.images`. Use synchronized clocks. Samples expire after ten seconds and a launch checks them again after registration.

## Native worker contract and verification matrix

Native macOS and native Windows pools accept an explicit operator-supplied containment adapter and a trusted probe. Native macOS requires an Apple host or VM on Apple hardware. The adapter is a trusted local executable, configured as an absolute executable and arguments. It receives an operation name as its last argument and a JSON object over stdin containing `version: 1`, `owner`, and the pinned `node` identity. Its JSON response must repeat `version: 1` and the independently observed `identity`. The lifecycle contract is:

| Operation | Required behavior                                                                                                                                                                                             |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `inspect` | Report native `os` and `arch`, `native: true`, `appleHost: true` for macOS, available `templates` and `hardLimits` covering `cpu`, `memory`, `filesystems` and `process-tree`.                                |
| `launch`  | Register/start one clean native runner under the supplied `lease`, `template`, `platform`, `origin`, one-time `ticket` and `limits`. The host containment must be active before the runner can pick up a job. |
| `list`    | List all `workers` owned by the controller with a stable `id` and `state` of `live` or `terminal`. Retain identity across controller restarts.                                                                |
| `remove`  | Purge an exited or absent worker by its `lease`. Preserve other workloads and handle repeated cleanup.                                                                                                        |

Inside a contained guest, run [native-worker.mjs](../examples/hive-runners/local/native-worker.mjs) with a JSON config path as its first argument. Set `workspace` to the guest's writable runner directory and `runner` to the absolute `Runner.Listener` (`Runner.Listener.exe` on Windows) or GitLab Runner executable. Send only `platform`, `origin` and `ticket` as JSON over stdin. The guest launcher registers with the provider, runs a one-job worker and exits when it finishes. Assign one clean guest per lease, install the matching runner version and architecture, and use the adapter's exit check to purge only that guest.

Hypervisor-backed native guests are a way to build such an adapter. Allocate fixed virtual RAM and bounded per-guest storage on an independently measured backing volume. Verify the hypervisor's CPU limit, avoid unrestricted host shares and give each guest a fresh runner identity. A process-only shell wrapper or a native GitLab shell executor by itself cannot establish whole-tree resource and disk isolation. No turnkey native VM adapters ship with this change. [Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) · [Hyper-V VM processor limits](https://learn.microsoft.com/en-us/powershell/module/hyper-v/set-vmprocessor) · [Tart macOS virtualization](https://tart.run/)

| Controller and runtime                                       | Worker OS and architecture                          | Evidence                                                                                                        |
| ------------------------------------------------------------ | --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Linux Docker Engine, cgroup v2                               | Linux amd64, arm64                                  | Hosted kernel probes verified two workers on each architecture. Real private provider jobs pending.             |
| macOS Docker Desktop Linux containers                        | Linux amd64 or arm64, same as VM                    | Linux engine protocol and separate host/VM claims. Physical Intel and Apple Silicon verification pending.       |
| Windows Docker Desktop Linux containers                      | Linux amd64 or arm64, same as VM                    | Linux engine protocol and separate host/VM claims. Windows and Desktop hardware verification pending.           |
| Single-node Swarm                                            | Linux amd64, arm64                                  | Hosted amd64 probes verified two tasks on the pinned node. Arm64 and private jobs pending.                      |
| Distributed Swarm                                            | Linux amd64, arm64                                  | Automated placement and scheduler checks. Real distributed cluster and private jobs pending.                    |
| kind Kubernetes                                              | Linux amd64, arm64                                  | Hosted amd64 probes verified two restricted pods on separate pinned nodes. Arm64 and private jobs pending.      |
| Full Kubernetes, Minikube, Docker Desktop Kubernetes and k3s | Linux amd64, arm64                                  | Shared Kubernetes worker spec and automated scheduling checks. Distribution, hardware and private jobs pending. |
| Apple hardware, native macOS or macOS-native VM              | macOS amd64, arm64                                  | Requires an operator-supplied adapter. Native integration and private jobs pending.                             |
| Windows native host or Windows-native VM                     | Windows amd64, arm64                                | Requires an operator-supplied adapter. Native integration and private jobs pending.                             |
| Windows-container mode or emulated worker architecture       | Windows containers or non-native Linux architecture | Unsupported. Config and engine preflight reject these modes before registration.                                |

An acceptance run on each environment starts two routed private jobs using the [GitHub workflow](../examples/hive-runners/local/github.workflow.yml) or [GitLab pipeline](../examples/hive-runners/local/gitlab-ci.yml), verifies architecture and workspace containment, rotates the admin credential, restarts during work, drains under CPU/RAM/storage pressure and confirms full cleanup and recovery. Save the job URLs and worker and node identities for each run. The hosted [Linux containment workflow](../.github/workflows/local-workers.yml) checks cgroup CPU and RAM ceilings, CPU accounting for a child process, tmpfs memory accounting and write rejection beyond the workspace and temporary-filesystem limits. The provider test templates and bounded probes carry no private credentials.

## Upstream components and design choices

- Docker Engine and Swarm provide CPU and memory controls and Swarm node constraints. Docker writable-overlay quotas depend on the storage driver and backing filesystem. Read-only images and bounded tmpfs avoid relying on a particular writable overlay quota implementation. [Docker run options](https://docs.docker.com/reference/cli/docker/container/run/) · [Swarm service options](https://docs.docker.com/reference/cli/docker/service/create/)
- Kubernetes handles node placement and CPU and RAM enforcement. Kubelet local ephemeral-storage limits commonly depend on measurement and eviction, so the workspace uses a size-limited memory-backed volume. Linux cgroup v2 provides shared accounting for descendant processes. [Kubernetes resource management](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/) · [Linux cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)
- GitHub ARC and GitLab autoscalers remain options for cluster or fleet deployments. GitHub's JIT API and GitLab Runner's one-shot shell executor let the local controller own the timing of worker registration and reconcile one resource lease per worker. [GitHub self-hosted runner API](https://docs.github.com/en/rest/actions/self-hosted-runners) · [GitLab Runner commands](https://docs.gitlab.com/runner/commands/)
