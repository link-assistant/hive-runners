# Issue 1 case study

[Issue #1](https://github.com/link-assistant/hive-runners/issues/1) asks for a private GitHub Actions fleet that can start with a single inexpensive VPS, scale jobs and machines, and support paid capacity and resellers. The issue capture, sub-issue list and discussion snapshots are in [data](data/). The issue has no listed sub-issues. The later PR review requested the associative stack, configurable UI, monitoring, Linux-only CI, and a competitor analysis. The next review added GitLab parity, NVIDIA GPUs, mixed hosts, isolation choices, resource sizing, and exact purchasing terms. [Mixed fleet feedback](https://github.com/link-assistant/hive-runners/pull/2#issuecomment-7035306001) · [Earlier review feedback](https://github.com/link-assistant/hive-runners/pull/2#issuecomment-7032593959)

## Primary source research

- GitHub scale-set names can be reused across multiple clusters when assigned to distinct runner groups. GitHub directs operators to set minimum and maximum to zero when draining a queue. [Deploy ARC runner scale sets](https://docs.github.com/en/actions/how-tos/manage-runners/use-actions-runner-controller/deploy-runner-scale-sets)
- GitHub documents different permissions for repository and organization registration, runner-group administration, and signed workflow job deliveries. [ARC authentication](https://docs.github.com/en/enterprise-cloud%40latest/actions/how-tos/manage-runners/use-actions-runner-controller/authenticate-to-the-api) · [Runner groups](https://docs.github.com/en/rest/actions/self-hosted-runner-groups) · [Workflow job webhook](https://docs.github.com/en/webhooks/webhook-events-and-payloads#workflow_job)
- Contabo documents Cloud VPS 6 with 6 vCPU, 12 GB of memory and a 200 GB SSD option. Its public API is the basis for the capacity adapter. [Contabo VPS specifications](https://docs.contabo.com/docs/servers-hosting/vps/) · [Contabo API](https://api.contabo.com/)
- Hetzner’s adjustment table lists a USD 6.49 monthly cap for CX23 in the relevant low-cost market, excluding public IPv4 and VAT. Its API supports server creation, listing and deletion. [Hetzner cost table](https://docs.hetzner.com/general/infrastructure-and-availability/price-adjustment/) · [Hetzner Cloud API](https://docs.hetzner.cloud/reference/cloud)
- Minikube supports the Docker driver. Kubernetes network policies depend on a compatible enforcement plugin, which is why the playbook selects Calico. [Minikube Docker driver](https://minikube.sigs.k8s.io/docs/drivers/docker/) · [Kubernetes network policies](https://kubernetes.io/docs/concepts/services-networking/network-policies/)
- Stripe recommends fulfillment from events and checking payment status. Session creation and fulfillment are distinct operations. [Stripe Checkout fulfillment](https://docs.stripe.com/checkout/fulfillment) · [Stripe webhooks](https://docs.stripe.com/webhooks)

- GitLab’s Kubernetes executor provisions a separate pod for each job. Runner authentication, tags, runner scope and job events come from GitLab’s official interfaces. [Kubernetes executor](https://docs.gitlab.com/runner/executors/kubernetes/) · [GitLab Helm chart](https://docs.gitlab.com/runner/install/kubernetes/) · [Runners API](https://docs.gitlab.com/api/runners/) · [Job events](https://docs.gitlab.com/user/project/integrations/webhook_events/#job-events)
- NVIDIA’s device plugin advertises whole GPU resources to Kubernetes. Admission verifies the device count before publishing the pool. [Minikube NVIDIA integration](https://minikube.sigs.k8s.io/docs/tutorials/nvidia/) · [NVIDIA device plugin](https://github.com/NVIDIA/k8s-device-plugin)
- Hive Mind reserves capacity before starting queued work and budgets container CPU and memory explicitly. The fleet controller applies these ideas to provider quotas, running and queued work, and host admission. [Queue start reservations](https://github.com/link-assistant/hive-mind/blob/main/src/queue-start-reservation.lib.mjs) · [Container resource limits](https://github.com/link-assistant/hive-mind/blob/main/src/container-resource-limits.lib.mjs)

## Verification sequence

1. Validate generation and provider schemas. Lint and render the control-plane chart and official runner charts. Syntax-check both Ansible playbooks.
2. Use the JavaScript acceptance suite for signed events, durable usage, payments, quote matching, mixed-host sizing, scope constraints and provider lifecycle. Use browser checks for responsive navigation, portal authentication and activation.
3. Register GitHub repository and organization pools and GitLab project and group pools using authorized private CI repositories. Queue concurrent CPU and GPU jobs on dedicated and mixed configurations, verify device visibility and isolation, and observe drain.
4. Exercise completed payment, refunds and wholesale usage with signed fixtures and two local control planes. Validate provider request shapes and retirement with mocked APIs. The latest review waived automated external VPS purchases, retirements and Stripe test-mode operations.

Steps 1, 2 and 4 use local verification and Linux CI. Step 3 needs authorized private GitHub and GitLab scopes and Linux test hosts with an NVIDIA device. The workspace has access to the pull request and lacks those test resources.
